# React and native dependency resolution

Validated on Windows x64, Node 24.16.0/npm 11.13.0, 2026-09-19 UTC.
Scope: dependency resolution, shared provider rendering, and Expo file-adapter
compatibility. No release, deployment, account access, or feature removal.

## Web: two installed versions, one bundled React

Raw Node resolution alone is misleading in this monorepo:

| Importer | Raw Node React resolution | Actual web Vite resolution |
| --- | --- | --- |
| Web application / web React DOM renderer | `apps/web/node_modules/react`, 18.3.1 | Web React 18.3.1 |
| Shared ServicesProvider | Root `node_modules/react`, 19.1.0 | Web React 18.3.1 |
| Shared AuthProvider | Root `node_modules/react`, 19.1.0 | Web React 18.3.1 |
| Shared DataProvider | Root `node_modules/react`, 19.1.0 | Web React 18.3.1 |
| Mobile / React Native | Root React 19.1.0 | Not part of the web bundle |

The installed `@vitejs/plugin-react@4.7.0` already contributes
`resolve.dedupe: ["react", "react-dom"]`. The existing web configuration uses
that plugin. An additional alias or React major upgrade was therefore unnecessary;
Vite and Metro configuration remain unchanged. Mobile keeps React 19.1.0 and
React Native 0.81.5 as required by Expo 54.

`scripts/react-resolution.test.mjs` verifies the effective development resolver
for React and both JSX runtimes from the renderer and all three shared providers.
It also builds a client-side fixture with the real web plugins and resolution
configuration, checks the Rollup module graph for one React package root, and
mounts ThemeProvider, ServicesProvider, AuthProvider and DataProvider in jsdom.
The test waits for signed-out auth/data effects, checks service context identity,
and clicks a button to verify a state update with no rendering errors.

The fixture uses synthetic auth only; unexpected service access throws. It does
not contact Firebase or AI services. It is outside the application entry graph
and is included in web typechecking. The DOM test is not a full browser E2E test,
an authenticated-session test, or proof that all application behavior is correct.
The fixture uses a single output chunk for execution; the normal web build is
validated separately with the production chunk configuration.

## Explicit mobile release exclusions

The web gate does not certify mobile release readiness. Mobile ownership must
close all of the following before distributing a native build:

1. **Firebase persistence compatibility:** Firebase 11.10.0's
   `@firebase/auth@1.10.8` declares optional AsyncStorage peer `^1.18.1`, whereas
   Expo 54 requires 2.2.0. `npm ls @react-native-async-storage/async-storage --all`
   exits 1 and reports that peer invalid. A single installed version and successful
   bundling do not resolve the declared mismatch. No override, legacy-peer mode,
   or unsupported AsyncStorage downgrade masks it. Qualify a compatible Firebase
   update separately, including auth persistence across app restarts on devices.
2. **Existing mobile type error:** `profile.tsx:76` omits the required MenuRow
   `description`. `npm run typecheck:mobile` remains a failing baseline check.
   Existing mobile lint and repository formatting debt also remain tracked in
   [the development baseline](development-baseline.md).
3. **Device import/export qualification:** on both Android and iOS, test canceled
   picker, a UTF-8 CSV containing non-ASCII text, cache-copy readability, JSON
   export through the share sheet, reopened exported JSON, unavailable sharing,
   and auth restoration after restart. No device runtime was used in this task;
   real-device compatibility is not claimed.

These are explicit native-release exclusions, not ignored passes in the baseline.
