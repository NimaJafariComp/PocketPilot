# Reproducible development baseline

Subsequent React/native dependency work and its current qualification limits are
recorded in [Dependency resolution](dependency-resolution.md). The original
results and lock hash below are the historical P0-01 snapshot, not the newer lock.

## Toolchain and installation

Use Node **24.16.0** and npm **11.13.0** from the repository root. `.nvmrc`,
`packageManager`, and `engines` record these versions; the baseline runner checks
them before running. Node 24 is an LTS line and meets Expo SDK 54's minimum
Node 20.19.4 requirement. This is a tested development pin, not a claim that it
is the latest security patch. Dependency/security upgrades require separate review.

```sh
npm ci
npm run baseline
# Or record the clean installation together with every check:
npm run baseline -- --install
```

`npm ci` removes the existing installation before installing the frozen lockfile.
Do not run concurrent installs, builds, or development servers during this step.
The baseline executes every check independently, saves logs and `summary.json`
under ignored `work/baseline/run-*`, and exits nonzero if any check fails or the
root lockfile changes. No application servers or cloud resources are started.
Each child process has a ten-minute timeout; a timeout is a failure, not a pass.

The host pin does not migrate Docker or the separate Functions runtime. Neither
Docker execution, Functions compilation nor a native-device run is certified by
this baseline. The existing Docker convenience script still performs its own
install and is not the frozen baseline workflow.

## Lockfile ownership

- `package-lock.json` is authoritative for the root, `apps/*`, and `packages/*`.
  Install only from the root; use root `npm install` for intentional dependency
  changes, then review and commit manifest and lockfile changes together.
- `backend/functions/package-lock.json` is authoritative for Functions, which is
  not a root workspace. Its declarations are checked separately; its packages
  are not installed by root `npm ci`.
- `apps/web/package-lock.json`, `apps/mobile/package-lock.json`, and
  `packages/services/package-lock.json` are retained historical lockfiles, not
  inputs to workspace installation. Do not regenerate them with nested installs.

`npm run check:lockfiles` compares dependency declarations in every workspace and
Functions against their authoritative lock entries. It also checks the native
Rollup, esbuild, and Tailwind oxide platform records that previously prevented a
Windows build. This is a targeted metadata guard; frozen installation remains
the authoritative npm graph validation.

The repaired lockfile retains all previously resolved package versions. Added
records are focused test-tool dependencies and missing optional native-tooling
metadata generated by npm. No force-upgrade or dependency audit fix was applied.

## Independent checks and ownership

| Command | Owner | Purpose |
| --- | --- | --- |
| `npm run check:lockfiles` | Platform | Manifest/lock and native metadata consistency |
| `npm run test:unit` | Domain + platform | CSV, dedupe, goals and lock guard tests |
| `npm run typecheck:web` | Web | Strict web source and Vite configuration check |
| `npm run typecheck:core` | Domain | Strict shared domain check |
| `npm run typecheck:services` | Platform | Strict shared service/platform adapter check |
| `npm run typecheck:mobile` | Mobile | Existing Expo TypeScript check |
| `npm run web:build` | Web + platform | Production Vite build |
| `npm run lint` | Frontend/mobile | Existing Biome lint policy |
| `npm run format:check` | Frontend/mobile | Existing Biome formatting policy |
| `node apps/mobile/scripts/verify-runtime-deps.cjs` | Mobile | Existing runtime-dependency guard |

`npm run typecheck:shared` is a convenience wrapper. The baseline invokes core
and services separately so a core failure cannot hide a services result.
Tests use synthetic data. Three CSV cases remain explicit TODOs (malformed
amounts, ambiguous locale amounts, impossible non-ISO dates); TODO is not proof
of correct behavior. Fix those during strict import validation, not by asserting
the current incorrect output.

## Observed results (2026-09-18 local / 2026-09-19 UTC)

On Windows x64 with the pinned toolchain, the original clean install succeeded
but the web build failed because the lock lacked the Windows Rollup binary.
After npm regenerated the missing platform metadata, the web build passed.
Web, core, services, runtime dependency guard, lockfile checks, and all 17
executable unit tests pass. Three additional tests remain TODOs.

A second local checkout of the original commit, with only the implementation
files overlaid (no node_modules or private planning document), reproduced these
results using `npm run baseline -- --install`. It used LF checkout rules and
reported 14 formatting errors. The root lock SHA-256 was identical in both
checkouts and unchanged by clean installation:
`b55f1969e0657f0f92ff4f794718da445d01d2139db89c30c41a164f15b09676`.
The fresh run completed at `2026-09-19T04:29:11.739Z`. This verifies Windows
resolution; other operating systems still need their own execution evidence.
